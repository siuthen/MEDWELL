# 생산계획

생산계획은 `productions`에 추가되며 기존 API와 과거 기록은 유지한다. 기존 입고·재고 계산은 변경하지 않는다. 새 계획은 `kind: productionPlan`, `plannedQty`, `fileName`, `source`와 확정 당시의 `version` 및 자재 차감 `lines`를 저장한다. `normal`에는 계획수량, `retained`에는 0을 함께 저장하여 기존 소비자와 호환한다.

업로드는 재고 업로드의 15MB/압축 해제 제한을 공유하며 최대 5,000행을 허용한다. 완제품 코드와 계획수량 헤더는 필수이며, 계획일은 화면 기본 계획일(초기값: 한국 시간 오늘), 창고는 화면 기본 차감 창고를 적용한다. 인식할 수 없는 비어 있지 않은 시트나 오류 행이 있으면 확정을 막는다. 음수 예상재고는 경고하되 허용한다.

`bulkProductionPlan`은 모든 행을 서버에서 재검증한 다음 한 번의 상태 CAS로 저장한다. 승인된 BOM 또는 `pre_2023_only`만 허용한다. 업로드당 감사로그 한 건에 파일명·계획 건수·차감 라인 수를 기록한다. 기존 version과 requestId 처리로 동시 저장 충돌과 중복 차감을 방지한다.

재고는 미취소 기록의 저장된 차감 라인으로 계산한다. BOM 마스터를 나중에 수정해도 이미 확정한 계획은 달라지지 않는다. 같은 제품의 계획수량 수정은 최초 스냅샷을 비례 조정하며 제품 변경 시 현재 제품 BOM을 새로 검증·저장한다. 취소는 기록을 보존하고 차감만 해제한다. 과거 기록에는 자동으로 새 필드를 쓰지 않는다.

테스트는 로컬 메모리 상태와 모의 DB만 사용한다. `tests/production-plan-api.test.mjs`는 실제 POST 함수를 모의 DB에 연결해 전체 실패, version 충돌, 동시 CAS, 중복 요청, 서버 BOM 검증을 검사한다. 운영 API로 테스트 전표를 만들지 않는다. 전체 테스트는 `tests/*.test.mjs` 각각을 `node`로 실행하고 타입 검사는 `tsc --noEmit`, 배포 빌드는 `npm run build`로 검사한다.


## 병합형 보고서 미리보기

일반 코드·수량 표를 우선 인식한다. 일반 헤더가 없는 표시 XLSX 시트에서만 제품생산계획수량 제목, J열 제품 계획 보고란·계획수량, B/C/D열 순번·품명·용량을 함께 확인한다. B열 월별 순번과 C/D 값이 있는 행만 제품 행으로 추출한다. J열은 숫자 뒤 개·박스·EA 단위를 허용하고, 박스 내용물 수를 곱하지 않는다. 원본 파일은 코드나 테스트에 포함하지 않는다.

제품 추천은 정규화된 이름과 용량(세트 구성 수 포함)이 일치하는 활성 제품이 하나일 때만 적용한다. 접두사·괄호 설명·공백·플러스 표기를 정규화하되 부분 이름 검색, 유사 철자, 용량 추측으로 선택하지 않는다. 후보가 여러 개이거나 없는 경우 사용자가 활성 제품을 선택하거나 해당 행을 제외해야 한다.

포함 체크는 업로드 화면의 선택 상태이며 운영 데이터에 저장하지 않는다. 제외된 행은 오류 집계·자재 합계·확정 payload 모두에서 빠진다. 기본 날짜·창고 변경과 제품 선택은 미리보기를 즉시 다시 계산한다. 서버 bulkProductionPlan 검증, 저장 구조, 원자 처리, 취소·입고 로직은 그대로 유지한다.
